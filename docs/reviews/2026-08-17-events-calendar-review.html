01

What we're building

decided

Local organizers submit an event. It appears on the calendar and the map within seconds. People who want to come join a Signal group, and the organizer tells them where to go in there.

Two kinds of event, and the difference matters:

How the two event types differ
MeetupPublic event
ExampleSign night, canvass, organizing meetingCounty council ALPR vote, public hearing
AddressNever publishedRequired, published
DescriptionNone — title onlyUp to 300 characters
Signal groupRequiredOptional
Why meetups have no description field at all. Anything published without a human reading it first is a place someone can write something defamatory under our domain. A title we can cap at 80 characters is a much smaller target than a paragraph, and for the description specifically, deleting the field beats trying to police it. The title that remains still gets a full sanitization pass.
02

How it works

decided

The site stays static. A small function accepts submissions and writes them to storage; the calendar page is pre-built from a file in the repo and merges in anything newer. Once a week a scheduled job folds storage back into the repo.

One property worth calling out. Because Signal links resolve through /go/:id rather than sitting in the page, they never need to be in the committed file either. Git history is permanent and public. No Signal link submitted through this calendar enters the repository. (The separate poster generator keeps one in its own config, so this holds for the calendar pipeline rather than the repo as a whole.)

04

Organizer codes

decided

An organizer code is a four-word passphrase, something like drum-yoga-vivid-clay. One person, one code, handed over after an actual conversation. It is the last field on the submission form and the only thing standing between that form and the live site.

Why there is a code at all. Events go live the moment they are submitted, with nobody reading them first. Something has to establish that a submission came from a person we have spoken to rather than from anyone who found the form. That is the code’s whole job.

Why not accounts. A login system means storing email addresses, password hashes, and a reset flow. Every one of those is something that can be breached, and something that can be subpoenaed. For a project whose entire argument is that surveillance infrastructure gets abused, keeping a database of organizer identities is the wrong shape. A code proves somebody was vetted without recording who they are: we store a pseudonym, and the mapping from pseudonym to person stays offline, wherever the vetting conversation happened.

Why not just review every submission. That works, and it is genuinely simpler. It also costs a human read on every event, and it means an organizer who posts a meetup on Tuesday might not see it appear until Thursday. We chose speed for organizers over a review queue, and the code is what makes that choice survivable.

Why four words. About 2.8 trillion combinations, so guessing is pointless: at a million attempts a day against every code we have issued, it would take tens of thousands of years. Short enough to read down a bad phone line or type from memory, and the wordlist is built for exactly that, with no two words sharing their first three letters.

When one leaks. And one will, eventually, by entirely ordinary means: a screenshot, a forwarded message, a phone photographed at a meeting. Revoke it, and every event posted with it comes down in the same action. That is the reason codes are individual rather than one shared password everybody knows.

How one gets issued. A small script in the repo generates a code, shows it once so you can copy it across, and writes only its hash to the store. That is the single moment the plaintext exists: it is never saved to a file, never printed again, and never committed. Revoking runs the same script. Both take effect immediately, with no deploy and nothing to merge.

What a code cannot do. It proves who submitted, never what they submitted. A real organizer typing the wrong address, or writing something they should not have, passes the check exactly as cleanly as a careful one does. The code is not a substitute for the review we chose not to do, and it should not be described to anyone as though it were.

Before you paste that link

Four things, once per group.

  1. Give it a boring name and leave the description blank.

    Anyone holding the link can read your group's name, description, and member count without joining. "Thursday group" tells them nothing. "Greenville DeflockSC organizers" tells them your chapter exists and how many of you there are. The address never goes in the description.

  2. Set disappearing messages before you invite anyone. Group Settings › Disappearing Messages

    1 week is a fine default. Do it first, or the early messages stay forever.

  3. Hide your own number. Settings › Privacy › Phone Number › Nobody

    Set a username instead. You're about to be in a room with strangers.

  4. Burn the group when the event's over.

    Have everyone leave, then delete it. Move the people you trust into a separate group. Don't reuse an event group for anything else, and only keep one alive if the event actually recurs.

Step 1 needs checking before we ship it. It rests on the claim that anyone holding a Signal group link can read the group's name, description, and member count without joining and without tripping an approval request. If that's true, scraping our calendar yields a roster of every chapter and its size. We could not confirm it against Signal's own documentation. If you have a Signal group, please test this and tell us.
We deliberately do not tell organizers to turn on "Approve new members". The group is meant to be open so strangers can find it. The protection here is that the group is temporary and gets destroyed, not that it has a door.

07

The privacy posture

needs input

This is the part most worth arguing about, because it's the part where we could mislead people without meaning to.

What the calendar publishes and what it never collects
PublishedNever published
MeetupTitle, date, time, city, county, organizer pseudonymAddress. The organizer's name, email and phone are never collected at all.
Submission—The submitter's IP, hashed on arrival and never stored in the clear
Git historyEverything above, permanentlySignal links, which live only in the runtime store
What withholding the address actually protects. It protects the venue and whoever hosts it. A library, a church, or somebody's house never gets indexed, never shows up in a search, and never gets the phone calls pressuring them to cancel. That's real and it's worth doing.
What it does not protect, and we should say so out loud. Publishing a city plus an exact date plus an exact time hands over both inputs an ALPR query needs. Someone with Flock access doesn't need our address: they pull every plate through that city's cameras across the meeting window, pull again at the end, and intersect the two. In a small town that's a short list. Withholding the street address does not touch the technology this organization exists to oppose.

We're publishing date and time anyway, knowingly, because a calendar without them isn't much of a calendar. What follows from that is a copy decision rather than a technical one: the site should not imply the protection is broader than it is, and it should tell people the useful thing. Carpool. Park a few blocks out. Ask about a ride.

Overselling a privacy control costs an anti-surveillance organization more than not having one.

08

Security, briefly

decided

Organizer codes, mechanically. Codes are stored as a keyed hash with a secret only the server holds, so a leaked store yields nothing usable. The hash doubles as the lookup key, which means there is no comparison loop to get wrong and no timing signal to exploit. Issuing and revoking both happen from a local script, instantly, with no deploy.

Signal links. Nothing links directly to signal.group. Links go to /go/<event>, which looks up the real link and forwards. That means the link isn't in the page for a scraper, isn't in search results, isn't in the Internet Archive, and isn't in git. It also means we can replace a group without touching the site, and any flyer already printed keeps working.

Being honest about what that buys. Scrambling links in the page wouldn't stop anyone determined; a dozen events is a dozen clicks. What the redirect actually gives us is that the links aren't sitting in a public archive forever, and that we can swap one out in a single edit. Treat it as hygiene, not armor.

Past events. The listing stays; the redirect refuses to resolve. Because the link was never in the page, there's nothing to strip.

If a code leaks. Revoke it, and every event posted with it comes down. Codes leak by ordinary means, a screenshot or a photographed phone, and it's undetectable when they do, so the response has to be fast rather than clever.

Full technical specification lives at docs/plans/2026-08-17-events-calendar-design.md on the feature/events-calendar branch. It carries the parts left out here: validation rules, the exact hashing scheme, rate-limit mechanics, the credit and bandwidth measurements behind the weekly fold, and the test plan.

Nothing has been built yet. This is the design, up for argument.
